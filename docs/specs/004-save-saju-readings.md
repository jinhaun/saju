# 004 사주 해석 결과 데이터베이스 저장

## 목적

Google 로그인한 사용자의 성공한 사주 해석 결과를 Supabase Postgres에 저장하고, 사용자가 자신의 이전 결과만 다시 보거나 삭제할 수 있게 합니다.

## 의존성

- `002-gemini-reading.md`의 해석 생성과 응답 구조 검사가 완료되어 있어야 합니다.
- `003-google-login.md`의 Supabase Auth 세션이 구현되어 있어야 합니다.
- 로그인하지 않은 사용자의 결과는 데이터베이스에 저장하지 않습니다.

## 사용자 경험

1. 로그인한 사용자가 기존 화면에서 사주 해석을 요청합니다.
2. Gemini 해석과 서버 응답 구조 검사가 성공한 뒤 결과를 자동 저장합니다.
3. 저장 중에는 `결과를 안전하게 저장하고 있어요` 상태를 보여줍니다.
4. 저장에 성공하면 `내 결과에 저장됨`을 보여줍니다.
5. 저장에 실패해도 해석 결과는 그대로 보여주고 `저장 다시 시도` 버튼을 제공합니다. Gemini 해석을 다시 생성하지 않습니다.
6. 사용자는 `내 사주 결과`에서 최신순으로 자신의 기록을 보고 상세 결과를 열거나 삭제할 수 있습니다.
7. 로그인하지 않은 사용자는 해석 결과를 볼 수 있지만 `로그인한 결과부터 저장됩니다` 안내를 봅니다.

## 저장 시점과 저장하지 않는 경우

### 저장함

- 서버 입력 검사를 통과함
- `lib/saju`의 사주 계산이 성공함
- Gemini 호출이 성공함
- Gemini 결과가 `SajuReading` 구조 검사를 통과함
- 저장 시점에 유효한 로그인 사용자가 있음

### 저장하지 않음

- 입력 오류, 계산 오류, Gemini 호출 실패 또는 응답 형식 실패
- 로그인하지 않았거나 세션이 만료됨
- 사용자가 Google 로그인을 취소함
- 클라이언트가 임의로 보낸 사용자 ID

## 데이터 구조

테이블 이름은 `public.saju_readings`를 사용합니다.

| 열 | 형식 | 규칙과 용도 |
|---|---|---|
| `id` | `bigint identity` | 내부 기본키 |
| `request_id` | `uuid` | 같은 저장 요청의 중복 삽입 방지 |
| `user_id` | `uuid` | `auth.users(id)` 참조, 계정 삭제 시 함께 삭제 |
| `birth_date` | `date` | 사용자가 입력한 양력 생년월일, 1950-01-01부터 2026-12-31까지 |
| `birth_time` | `time`, nullable | 사용자가 입력한 출생지 기준 시각. `null`은 출생 시각을 모름 |
| `topic` | `text` | 허용된 여섯 주제 중 하나 |
| `question` | `text` | 선택 사항, 최대 200자 |
| `chart` | `jsonb` | 서버가 계산한 사주 세 기둥 또는 네 기둥·일간·오행 분포와 계산 기준 |
| `reading` | `jsonb` | 검증된 제목·요약·상세 영역 3개·행동 제안 2~3개 |
| `model` | `text` | 해석에 사용한 Gemini 모델명 |
| `schema_version` | `smallint` | 저장 구조 버전, 처음 값은 1 |
| `created_at` | `timestamptz` | UTC 기준 저장 시각 |

### 제약 조건

- `id`는 기본키입니다.
- `(user_id, request_id)`는 유일해야 하며 재시도 시 같은 결과가 두 번 저장되지 않습니다.
- `user_id`는 `auth.users(id)`를 참조하고 `on delete cascade`를 사용합니다.
- `birth_date`는 `date '1950-01-01'` 이상, `date '2026-12-31'` 이하 검사 조건을 둡니다.
- `birth_time`은 사용자가 시각을 모르면 `null`을 허용합니다.
- `topic`은 `relationship`, `career`, `wealth`, `social`, `strengths`, `yearly`만 허용합니다.
- `question`은 빈 값 또는 200자 이하만 허용합니다.
- `chart`와 `reading`은 JSON 객체만 허용합니다.
- `schema_version`은 1 이상이어야 합니다.

### 인덱스

- 기본 목록 조회와 RLS 필터를 함께 빠르게 처리하도록 `(user_id, created_at desc, id desc)` 복합 인덱스를 만듭니다.
- `user_id`가 인덱스의 첫 열이므로 외래키 삭제와 사용자별 조회에도 사용할 수 있습니다.

## 개인정보와 보존

- 생년월일, 출생 시각, 자유 고민은 개인정보가 될 수 있음을 첫 저장 전에 안내합니다.
- 저장 목적은 사용자가 자신의 이전 해석을 다시 보는 것으로 제한합니다.
- Gemini 프롬프트 원문, Google provider token, Supabase 인증 토큰, API 키는 저장하지 않습니다.
- Google 이메일·이름·프로필 사진을 `saju_readings`에 복제하지 않습니다.
- 이번 범위에서는 자동 만료 기간을 두지 않고 사용자가 직접 개별 삭제할 수 있게 합니다.
- 계정 삭제 기능을 나중에 만들 때 `on delete cascade`로 결과도 함께 삭제합니다.

## Data API 권한과 RLS

2026년 Supabase의 Data API 기본 노출 변경에 대비해 테이블 생성과 같은 마이그레이션에서 권한과 RLS를 명시합니다.

### 권한

- `anon` 역할에는 모든 권한을 주지 않습니다.
- `authenticated` 역할에는 `select`, `insert`, `delete`만 명시적으로 부여합니다.
- 결과는 수정하지 않는 기록으로 취급하므로 `update` 권한은 주지 않습니다.
- 앱에서는 secret/service-role 키로 RLS를 우회하지 않습니다.

### 사용자별 정책

- **SELECT:** `(select auth.uid()) = user_id`인 자신의 행만 읽을 수 있습니다.
- **INSERT:** 새 행의 `user_id`가 `(select auth.uid())`와 같을 때만 저장할 수 있습니다.
- **DELETE:** `(select auth.uid()) = user_id`인 자신의 행만 삭제할 수 있습니다.
- 모든 정책은 `to authenticated` 역할을 명시합니다.
- 브라우저가 보낸 `user_id`를 신뢰하지 않고 서버의 검증된 로그인 claims에서 가져옵니다.

## 서버 API

### `POST /api/readings`

- 입력: 기존 사주 입력, 검증된 해석 결과, `request_id`
- 서버 처리:
  1. 로그인 claims를 검증합니다.
  2. 입력을 기존 `validateInput`으로 다시 검사합니다.
  3. `lib/saju`로 chart를 다시 계산해 클라이언트가 보낸 계산값을 사용하지 않습니다.
  4. 해석 결과를 `parseReading`으로 다시 검사합니다.
  5. 사용자 ID는 claims에서 설정하고 RLS가 적용되는 사용자 세션으로 삽입합니다.
- 같은 `(user_id, request_id)`가 이미 있으면 기존 저장 ID를 반환하고 성공으로 처리합니다.

### `GET /api/readings`

- 로그인한 사용자의 결과만 `created_at desc, id desc` 순으로 조회합니다.
- 한 번에 20개를 가져오며 다음 페이지는 마지막 `created_at`과 `id`를 사용하는 커서 방식으로 조회합니다.
- 목록에는 날짜, 고민 주제, 해석 제목, 저장 시각만 반환하고 상세 JSON은 상세 조회에서 반환합니다.

### `GET /api/readings/:id`

- 요청한 ID가 자신의 행일 때만 전체 입력·chart·reading을 반환합니다.
- 다른 사용자의 ID와 존재하지 않는 ID는 내용 차이를 드러내지 않도록 같은 `찾을 수 없음` 응답으로 처리합니다.

### `DELETE /api/readings/:id`

- 자신의 결과만 삭제할 수 있습니다.
- 삭제 전 화면에서 대상 날짜와 주제를 보여주고 확인을 받습니다.
- 삭제 성공 후 목록에서 즉시 제거합니다.

## 실패 처리

1. **로그인 만료:** 결과는 보여주되 저장하지 않고 다시 로그인을 안내합니다.
2. **저장 실패:** Gemini를 다시 호출하지 않고 현재 결과를 유지한 채 저장만 재시도합니다.
3. **중복 요청:** 같은 `request_id`의 기존 결과를 반환합니다.
4. **목록 조회 실패:** 저장된 결과가 없다고 잘못 표시하지 않고 불러오기 실패와 재시도를 보여줍니다.
5. **삭제 실패:** 화면에서 결과를 제거하지 않고 다시 시도 안내를 보여줍니다.
6. **권한 거부:** 다른 사용자의 자료 존재 여부나 내용을 응답에 포함하지 않습니다.

## 화면 범위

- 로그인 상태에서 해석 결과 카드에 저장 상태를 표시합니다.
- `내 사주 결과` 목록과 상세 화면을 제공합니다.
- 목록은 최신 결과부터 보여주고 20개 단위로 더 불러옵니다.
- 삭제 버튼에는 텍스트 이름을 제공하고 키보드로 사용할 수 있어야 합니다.
- 저장·조회·삭제 오류는 `role="alert"` 또는 적절한 live region으로 알립니다.

## 제외 범위

- 다른 사용자에게 결과 공유
- 결과 수정과 메모 추가
- 여러 사람 사주 묶음 관리
- 관리자 전체 사용자 조회
- 통계·추천·광고 목적의 사용자 데이터 활용
- 자동 보존 기간과 백업 복원 화면
- 실시간 구독과 알림

## 마이그레이션 방식

- 현재 프로젝트에는 `supabase/` 폴더가 없으므로 구현 시 Supabase 로컬 구성을 먼저 초기화합니다.
- 초기화 후 별도 선언형 스키마 설정이 없다면 imperative migration 방식을 사용합니다.
- `supabase migration new create_saju_readings`로 실제 타임스탬프가 붙은 파일을 만든 뒤 테이블, 제약, 인덱스, grants, RLS 정책을 한 마이그레이션에 작성합니다.
- 구현 후 Supabase Advisors를 실행하고 마이그레이션 목록을 검증합니다.

## 완료 조건

- 로그인한 사용자의 정상 해석만 한 번 저장됩니다.
- 같은 저장 요청을 재시도해도 중복 행이 생기지 않습니다.
- 비로그인 사용자는 테이블을 읽거나 쓰거나 삭제할 수 없습니다.
- 사용자 A는 사용자 B의 행을 목록·상세·직접 ID 요청으로 볼 수 없고 삭제할 수도 없습니다.
- 저장 실패가 Gemini 해석 성공 결과를 가리지 않으며 저장만 다시 시도할 수 있습니다.
- Google 토큰, Supabase 토큰·비밀키, Gemini 키와 원본 프롬프트가 데이터베이스에 저장되지 않습니다.
- 사용자가 자신의 결과를 최신순으로 보고 개별 삭제할 수 있습니다.

## 테스트 계획

### 데이터베이스 자동 테스트

- 테이블, 기본키, 외래키, 유일 조건, 검사 조건, 인덱스가 존재합니다.
- RLS가 활성화되어 있습니다.
- `anon`의 select·insert·delete가 거부됩니다.
- 사용자 A가 자신의 결과를 insert·select·delete할 수 있습니다.
- 사용자 A가 사용자 B의 결과를 select·delete할 수 없습니다.
- 다른 사용자의 `user_id`로 insert할 수 없습니다.
- 같은 `(user_id, request_id)`를 두 번 insert하면 중복 행이 생기지 않습니다.

### API 자동 테스트

- 서버가 클라이언트의 `user_id`와 chart를 무시하고 claims와 재계산 결과를 사용합니다.
- Gemini 성공 후 저장 성공·실패·재시도·중복 요청을 각각 확인합니다.
- 잘못된 reading 구조와 201자 질문을 저장하지 않습니다.
- 목록 정렬과 20개 커서 페이지 이동을 확인합니다.
- 다른 사용자 ID의 상세·삭제 요청이 자료를 노출하지 않습니다.

### 실제 화면 확인

- 로그인 전 결과가 저장되지 않고 로그인 안내가 보입니다.
- 로그인 후 생성한 결과가 저장 상태로 바뀌고 목록에 나타납니다.
- 새로고침과 재로그인 후에도 같은 결과를 볼 수 있습니다.
- 저장 실패 뒤 해석은 유지되고 저장 재시도가 동작합니다.
- 결과 삭제 후 목록과 상세 주소에서 다시 나타나지 않습니다.
